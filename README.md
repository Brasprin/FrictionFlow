# FrictionFlow

**Supporting Focus Recovery and Re-engagement from Cognitive Disruptions**

FrictionFlow is a Chrome extension (Manifest V3) that supports students in recovering focus during academic writing tasks in Google Docs. Instead of blocking distractions, it passively logs writing behaviour (typing, pauses, scrolling, tab switches) and tracks **two things at once**: the writer's current phase — Planning, Translating or Reviewing (Flower & Hayes, 1981) — and whether they are still **Focused** or have become **Distracted**. When disengagement is detected, it offers a contextual recovery prompt.

Detection thresholds are **calibrated per participant** from a short instructed writing task, and study sessions include a **standardised distraction** — a memory card game at fixed times — so recovery can be compared fairly across conditions.

## Requirements

- **Google Chrome** (the extension uses the MV3 side panel API — use Chrome for smooth operation)
- **Node.js** ≥ 18 and npm

## Setup

### 1. Install dependencies

```bash
npm install
```

### 2. Build the extension

```bash
npm run build
```

This compiles the React side-panel UI and copies `public/` (manifest, content script, background worker, the distraction game) into `dist/`. The `dist/` folder is the actual loadable extension.

For active development, use watch mode so every save rebuilds automatically:

```bash
npm run build -- --watch
```

### 3. Load the extension in Chrome

1. Open `chrome://extensions`
2. Enable **Developer mode** (top-right toggle)
3. Click **Load unpacked**
4. Select the **`dist/`** folder inside this project

### 4. Google Docs API setup (document reading)

The extension reads the actual document text through the official **Google Docs API** — used for the real word count and for the AI recovery summaries. Without this setup everything still works, but word count falls back to keystroke approximation and recovery prompts are behavioural-signals-only.

1. Load the extension once (step 3) and copy its **ID** from `chrome://extensions`.
2. In [Google Cloud Console](https://console.cloud.google.com): create a project and enable the **Google Docs API** (APIs & Services → Library).
3. Configure the **OAuth consent screen**: External, *Testing* publishing status, and add the Google account(s) that will run sessions as **test users**.
4. Create credentials → **OAuth client ID** → application type **Chrome Extension** → paste the extension ID from step 1.
5. A client ID is **already configured** in `public/manifest.json` → `oauth2.client_id`. You only need to replace it if you create a new OAuth client (e.g. a different Google Cloud project); rebuild and reload the extension afterwards.
6. On the first session start, Chrome shows a one-time Google consent popup (read-only Docs scope). Approve it once; later sessions are silent.

> The extension ID is **pinned** via the `key` field in `manifest.json`, so it is `ikgpicdfmeeicjffigdodgbfgppopppc` on every machine and path — one OAuth client serves the whole team. The Google Cloud OAuth client must be registered to that ID. (The private key `extension-key.pem` is gitignored and only needed if the extension is ever packed as a `.crx`.)

### 5. Researcher settings (Options page)

Right-click the extension icon → **Options** (or `chrome://extensions` → FrictionFlow → Details → Extension options).

| Setting | Purpose |
|---|---|
| **Gemini API key** | Recovery summaries in intervention sessions are generated by **Gemini** (`gemini-3.5-flash`, free tier). Paste a key from [aistudio.google.com/apikey](https://aistudio.google.com/apikey). Stored only in the browser's local extension storage. Without a key everything still works — the recovery screen shows an empty state. |
| **Short calibration** | 30 s per calibration step, for testing the flow. Profiles captured this way are **always rejected**. |
| **Short distraction schedule** | Distractions at minutes 1, 3, 5 with 70-second games, for testing the flow. Sessions are **stamped as test runs** in the export. |

**Turn both testing options off before running a participant.** Both the Options page and the setup screen warn while either is on.

### 6. Running a participant

**Once per participant — calibration (12 minutes)**

1. Open a Google Doc and click the FrictionFlow icon — the side panel opens beside it
2. Enter the **participant ID**, then **Run calibration**
3. The participant writes in the document through three timed steps — **Plan** (3 min), **Write** (5 min), **Review** (4 min) — on one standard prompt
4. The panel shows them their own numbers (writing speed, reviewing speed, typical pause). The profile is saved under their ID

**Their session (one per participant)**

Each participant takes part in **one condition only** — baseline or intervention (between-subjects). Assign conditions **at random**, or from a balanced list drawn up in advance; never by convenience.

1. Enter the participant ID — the setup card should read **Calibrated ✓**
2. Enter a task name and objective from their own coursework, choose the **condition** (Baseline / Intervention), then **Start Task**
3. They write. At minutes **10, 25 and 40** a memory card game opens in a new tab for three minutes; they return to the document when told time is up
4. **Finish session** → analytics summary (hover or click any tile for its breakdown)
5. Complete the **questionnaire** (NASA-TLX, FSS, UEQ-S), then **Download session data** — the export embeds the questionnaire responses, so do it in that order

Downloading produces **three files**: the session JSON, a one-row CSV, and `<name>_trace.csv` — one row per 2-second classifier tick, used to validate detection.

> If the panel is closed before downloading, the finished session is still recoverable: the task-setup screen shows a "Previous session was not downloaded" banner with a download button until it's retrieved.

## Reloading after changes

Which reload you need depends on what changed:

| What changed | What to do |
|---|---|
| `src/` (React UI) | Rebuild → close and reopen the side panel |
| `public/background.js`, `public/manifest.json`, `public/distraction/` | Rebuild → reload the extension (↻ on `chrome://extensions`) |
| `public/content.js` | Rebuild → reload the extension **and refresh the Google Docs tab** (content scripts only inject on page load) |
| Manifest permissions acting strange | Remove and re-add the unpacked extension (last resort) |

> Note: `npm run build -- --watch` handles the rebuild step, but Chrome-side reloads are still manual.

## Study conditions

The session condition toggle on the task setup screen is the experiment's independent variable. The design is **between-subjects**: each participant is assigned to one condition and takes part in one session.

- **Baseline** — behavioural data is logged, but no recovery prompts ever appear (control condition)
- **Intervention** — a "Gentle Reminder" prompt appears when the system detects distraction, offering *Get Back to Work* (recovery summary), *Take a Break* (timed break, tracking suspended), or *Dismiss*

**Instrumentation is condition-blind.** `content.js` — the sensor — contains no condition branch at all; it never reads or receives `ff_task.condition`, and even fires `FF_CHECK_STUCK` in both arms (background does the gating). The **distraction task is identical in both conditions** — same times, same exposure, same card layouts for every participant. The only condition branches live in the side panel: suppressing the prompt, and where a break returns you to. Neither touches any measurement.

**During a scheduled distraction the reminder is held** until the participant returns to the document. The side panel stays visible across tabs, so showing it beside the game would pull intervention participants back early — shorter distractions than baseline, and H1 would measure distraction length rather than the prompt.

One asymmetry is inherent rather than a code issue: `resumptionMs` runs return-to-doc → first keystroke, so in the intervention arm it also contains time spent reading the prompt and summary — time baseline participants never spend. The export therefore also carries `adjustedResumptionMs` per episode and `avgAdjustedResumptionSec`, which subtract that interaction time (identical to raw in baseline). Report H1 both ways.

## Architecture

```
┌──────────────────────┐   chrome.storage.local    ┌───────────────────────┐
│  content.js          │ ────────────────────────▶ │  App.jsx (side panel) │
│  (in the Docs page)  │  ff_session, ff_trace,    │  8 screens: init →    │
│  sensors, two-label  │  ff_calibrations          │  calibration → prep → │
│  classifier,         │                           │  monitoring →         │
│  calibration capture,│ ◀──────────────────────── │  recovery/break →     │
│  decision trace      │   FF_* runtime messages   │  analytics → survey   │
└──────────────────────┘                           └───────────────────────┘
                     ┌──────────────────────┐   ┌────────────────────────────┐
                     │  background.js       │──▶│  distraction/memory.html   │
                     │  session watchdog,   │   │  memory card game, opened  │
                     │  Docs API, Gemini,   │   │  in a new tab at minutes   │
                     │  distraction schedule│   │  10, 25, 40                │
                     └──────────────────────┘   └────────────────────────────┘
```

- **`public/content.js`** — the sensor. Runs inside Google Docs; logs keystrokes (via Docs' text-event iframe), scrolls, selection gestures and visibility changes. Every 2 s it classifies **two labels**: the phase (Planning / Translating / Reviewing) and attention (Focused / Distracted), the latter judged against the participant's own calibrated baseline for the current phase. Accumulates time in each phase and distracted time *within* each phase, records distraction episodes (with task-resumption times, tagged induced or natural), writes a per-tick **decision trace** of the classifier's raw inputs, and runs **calibration capture**. Flushes to `chrome.storage.local`.
- **`public/background.js`** — the watchdog + API gateway. Opens the side panel on toolbar click; marks the session interrupted if the Docs tab closes or navigates away. Reads the document text via the Google Docs API (OAuth, read-only scope) on request: content.js asks for the real word count every 2 s, and recovery-summary generation reads the doc tail for context. **Document text is ephemeral** — used inside the request and never written to storage, logs, or exports; only the derived word count (a number) is persisted. Hosts **recovery-summary generation** (Gemini, schema-enforced JSON), gated in one place (60-s cooldown, key configured, never in baseline). Also runs the **distraction schedule** on `chrome.alarms`, which survive the MV3 service worker being put to sleep: opens the game, defers it during breaks or interruptions, and records when the participant returns.
- **`src/App.jsx`** — the UI. All eight screens in one file, polling storage for live data and messaging the content script for lifecycle events (`FF_START_TASK`, `FF_RESUME_TASK`, `FF_CANCEL_TASK`, `FF_BREAK_START`, `FF_BREAK_END`, `FF_CALIB_*`, `FF_FLUSH_TRACE`). Also owns the export (`buildSessionExport()` produces the JSON, the CSV and the trace CSV from one function so they can never drift).
- **`public/distraction/memory.html`** + **`memory.js`** — the standardised distraction. Card layouts are fixed in advance, so every participant faces the same boards. Self-contained; also runs standalone when opened as a file.
- **`analysis/compare-thresholds.mjs`** — re-scores a session's trace under the calibrated and the fixed thresholds against a human coding of the screen recording, reporting agreement and Cohen's kappa for each.

### Storage keys

| Key | Written by | Purpose |
|---|---|---|
| `ff_task` | side panel | Task metadata: participant ID, name, objective, condition, start time, session tab id |
| `ff_session` | content.js | Live behavioural metrics, flushed every 2 s |
| `ff_interrupted` | background.js | Set when the Docs tab closes/navigates mid-session |
| `ff_idle` | content.js | Long-idle marker (≥ 2 min without activity) |
| `ff_draft` | side panel | Form contents stashed when a connection attempt fails |
| `ff_recovery` | background.js | Generated recovery summary; cleared at every session boundary |
| `ff_generating` | background.js | In-flight generation marker (a timestamp, so a stale one can be ignored) |
| `ff_settings` | options page | Researcher settings — Gemini API key and the two testing options |
| `ff_events` | side panel | Intervention events: prompt shown, response, voluntary break |
| `ff_suggestion_choices` | side panel | Which of the three suggestion stances was chosen, with the rejected options |
| `ff_lastSummary` | side panel | Finished-session export safety net; survives until the next session finishes |
| `ff_calibrations` | content.js | Calibration profiles, keyed by participant ID — one per participant, so calibrating one participant never overwrites another |
| `ff_trace` | content.js | Per-tick decision trace: the classifier's raw inputs alongside the decision they produced |
| `ff_distraction` | background.js | The scheduled distraction currently in progress, if any |
| `ff_distractions` | background.js | Every scheduled distraction this session: when it opened, deferrals, when the participant returned |
| `ff_game_logs` | distraction game | The memory game's own log per distraction: flips, matches, boards, and when "time's up" appeared |
| `ff_distraction_plan` | background.js | The distraction schedule fixed at session start, including whether it is a short-schedule test run |

> `ff_events` and `ff_suggestion_choices` are **panel-owned and deliberately kept out of `ff_session`** — content.js read-modify-writes that key continuously, so anything the panel wrote there would be clobbered.

## Detection thresholds

Thresholds are **per participant**, computed from their calibration run — for example, how long a pause has to be before it counts as unusual is measured separately for each phase, because a long pause is normal while planning and a stall while drafting. Each threshold and its formula is in [`CALIBRATION_SPEC.md`](CALIBRATION_SPEC.md) §6.

A participant is flagged **Distracted** by either:

- a categorical trigger — off the document tab for more than 60 s, or no interaction at all for 3× their personal pause threshold; or
- **two different signal families at once** — a long gap, a collapsed interaction rate, rapid tab-switching. One signal alone never flags anyone.

Without a valid calibration profile, a session falls back to documented default thresholds and is recorded as `calibrationValid: false` in the export.

## Current status

**Working and tested in simulation:** behavioural logging, the two-label classifier, per-participant calibration, time-in-phase and distracted-time-within-phase analytics, distraction episodes with resumption times (H1 measure) tagged induced or natural, baseline/intervention conditions, the Gentle Reminder (held during scheduled distractions), break mode, session interruption/resume, real word counts via the Docs API, **AI recovery summaries** (Gemini, pre-generated at distraction onset; honest empty state when no key is configured or generation fails) with **three distinct next-step suggestions** (goal-anchored / doc-driven / bridge) and per-session tallying of which was chosen, the **scheduled memory-game distraction**, the **decision trace**, and the **threshold-comparison analysis script**.

**Also working:** participant ID and session number, intervention-event logging, **session data export** (rich JSON, a single-row CSV, and the trace CSV, all from one builder), an un-downloaded-session safety net, per-tile hover breakdowns on the analytics screen, and **in-panel post-session questionnaires** — NASA-TLX (raw, 6 items), Flow Short Scale (10 items), UEQ-S (8 items) — whose subscale scores *and* every raw item ride in the same export.

**Not yet run in Chrome end to end** against a real participant session — see [`HANDOFF.md`](HANDOFF.md) §3.

**Not yet implemented (optional):**
- 50-minute session timer / end-of-session signal — currently timed externally by the researcher
- Recovery cooldown determinism: `lastRecoveryTime` lives in service-worker memory, which MV3 recycles after ~30 s idle, so "summaries generated per session" isn't reproducible across runs (no data-integrity risk — condition gating is independent)

## Known limitations

- Two word measures are reported and they legitimately disagree. **"Added this session"** is Docs API ground truth (synced every 2 s, minus a session baseline so pre-loaded prompt text isn't counted) — real word boundaries, includes paste. **"Typed"** is keystrokes ÷ 5 (the standard WPM convention), an effort measure that never consults the document, which is why WPM is computed from it: pasting can't inflate it. Pasting moves only the first; extending a word in place moves only the second; so Typed can exceed Added. Between syncs the live display drifts on the keystroke estimate and is corrected at the next sync; with no OAuth there is no ground truth at all and both fall back to the estimate (paste, undo, and autocorrect uncounted)
- A single tab-away is tolerated up to 60 s; beyond that it is flagged. The system cannot verify that a longer tab-away was legitimate reference-checking — mitigate with self-contained writing prompts
- Rapid tab-switching (≥3 in 60 s) is one signal, not a verdict: a writer typing productively while switching tabs is never flagged on that alone
- The tab thresholds (60 s away, 3 switches/min) are **not** calibrated — nobody switches tabs during a controlled calibration task, so there is nothing to measure
- Switching to another *application* is detected via `document.hidden` and is indistinguishable from a tab switch. Distraction entirely outside the browser — a phone, a second monitor — is not observable, and is caught only through the resulting inactivity
- Reviewing is detected from scrolling and deletion runs. Motionless rereading (eyes only, no interaction) remains indistinguishable from a Planning pause — a fundamental limit of behavioural sensing without eye-tracking
- Calibration measures the three phases **separately**; in real writing they interleave. Whether the classifier recognises them mixed is tested against human-coded screen recordings, not by calibration
- Only Google Docs is supported as the writing environment

## Privacy

The extension records only keyboard/scroll/tab-switch *activity metrics* inside the writing interface — never the document text itself as stored data, and no external applications or websites are monitored. The decision trace and the distraction game's log are activity metrics too: numbers, timestamps and card flips, no text. Document text **is** read ephemerally through the Google Docs API (read-only scope) to compute the word count and, in intervention sessions, to generate recovery prompts — per the consent-form commitment it is never persisted to storage, logs, or exported data. See the study's informed-consent documents for the full data-handling protocol.
